# Audit A: how an agent is launched and reports back (Windows 11 native)

Auditor: win-auditor (audit A). Read-only. Repo: `C:\Users\nicol\Documents\Claude Project\Tars\tars` (upstream 1.9.0).
Scope: `electron/providers/**`, `hooks/**`, `electron/utils/statusline.ts`, PTY spawning, ACP, `cli-updater.ts`.
Every line number below was re-read on 2026-09-25. "Proved" means a command was run on this machine (commands in section 5.4); nothing was written in the repo.

## 0. Headline corrections to AUDIT-INITIAL

1. **The provider bash wrappers are dead code.** `buildScheduledScript` (20 implementations, all `#!/bin/bash` + `source ~/.zshrc` + nvm, 11 of them `jq -r` on `app-settings.json` via `DATA_DIR_SHELL`) and `buildScheduledCommand` (20 implementations) have **zero production callers** (whole-repo grep: only the contract `cli-provider.ts:116,161`, the providers, `SPECS.md:130` and `__tests__/electron/providers/grok-provider.test.ts:128-142`). The local scheduler that used them is gone (Hermes is the scheduler now). Nothing to port; the "core of the problem" in AUDIT-INITIAL is not on the live path.
2. **The live launch path already builds the environment in Node.** All 20 providers put their env (`CLAUDE_AGENT_ID`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `AMP_API_KEY`, ...) into `pty.spawn(..., { env })` through `getPtyEnvVars`. What is Unix-only is (a) the shell: `/bin/bash -l` hardcoded, (b) the command line: a POSIX single-quoted string plus `cd '<dir>' && [exec]`, typed into or passed to that bash, (c) the PATH: `':'`-joined with Unix dirs.
3. **There are 20 providers, not 19** (`electron/providers/index.ts:33-54`), plus the virtual `local` which maps to claude. 14 run the `claude` binary, 6 have their own (codex, gemini, grok, opencode, pi, amp).
4. **Hooks fail three independent ways on Windows even with Git Bash installed**, all proved here: the unquoted backslash path in `settings.json`, `jq` absent, and `curl -H @<(...)` (process substitution) which Git Bash's mingw curl cannot read (exit 26).
5. **`cliRunningIn` is always true on Windows**: node-pty's `process` getter returns the terminal *name* (`'xterm-256color'`) on Windows, never the foreground process. Every "is a CLI running in this terminal?" decision (bots, agent:get, dispatch) is wrong.
6. **Typing a multi-line launch line into Windows PowerShell executes the second line as a command** (proved). Tars prompts contain `\n\n` (identity header + memory block), so a shell-typed launch is both broken and a command-injection vector on Windows.

Counts (exact):
- Interactive launch: **20/20** providers go through the same 4 consumer sites: `ipc-handlers.ts:787` (typed, `:844`), `agent-routes.ts:206` (`-c` + `exec`, `:246`), `bot-core.ts:305` and `:395` (typed, `:233`). One-shot: 1 caller, `kanban-generate.ts:47` (claude only, `exec`).
- 14/20 use the claude binary and the shared flag helpers (`promptOperand` in 14 files). 6/20 own binary.
- Agent PTY spawn sites: **5**, all through `spawnAgentPty` (`agent-pty.ts:65`): `agent-manager.ts:995`, `ipc-handlers.ts:391`, `:629`, `main.ts:576`, `agent-routes.ts:307`. Non-agent PTYs: 5 more (`pty-manager.ts:855`, `ipc-handlers.ts:185`, `:1346`, `:1537`, `:2920`).
- `configureHooks` does real work in 2 providers (claude, gemini); 18 are no-ops (13 empty bodies, 5 log lines).

- Dead bash: 20 `buildScheduledScript` (20 source `.zshrc`, 20 source nvm, 7 also bashrc/bash_profile, 11 use `jq`), 20 `buildScheduledCommand`.

Common pattern, fixable once: the providers are already platform-neutral in what they compute (flags + env); only the *serialisation* (POSIX string) and the *executor* (bash) are Unix. The fix belongs in one platform function between `buildInteractiveCommand` and `spawnAgentPty`, not in the 20 providers (see decision 2).

## 3. Per-hook table

All Claude hooks `source hooks/tars-hook.sh` (log dir `$HOME/.dorothy/logs`, `umask 077`, `mkdir -p`, `tars_auth` printf). ## 4. Already cross-platform (extend, do not duplicate)

- **Env built in Node for every provider** (`getPtyEnvVars`, 20/20): no shell export on the live path. Amp's managed settings file is written in Node (`amp-provider.ts:89-110`).

## 5. Research (with sources)

### 5.1 Hooks on Windows

- Claude Code, hook `command` without `args` (shell form): "passed to a shell: `sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash isn't installed". Per-hook `shell: "bash" | "powershell"`. Placeholders must be double-quoted in shell form. Source: https://code.claude.com/docs/en/hooks (fetched 2026-09-25, no page date).
- Claude Code exec form: with `args`, "Claude Code resolves `command` as an executable on PATH and spawns it directly ... There is no shell". On Windows "exec form requires `command` to resolve to a real executable such as a `.exe`. The `.cmd` and `.bat` shims ... can't be spawned without a shell. ... invoke the underlying script with `node` directly ... The `node` plus script-path pattern works on every platform because `node.exe` is a real binary." Hooks inherit the parent environment (except OTEL_* and optional scrub). Default command timeout 600 s. Same source.
- Claude Code HTTP hooks: `type: "http"`, `url`, `headers` with `$VAR` interpolation only for names in `allowedEnvVars`; the hook JSON is POSTed as the body, response uses the same JSON output format; subject to `allowedHttpHookUrls` if set. Same source. (Option C below.)
- Claude Code on native Windows: Git for Windows is optional; without it Claude uses the PowerShell tool; `CLAUDE_CODE_GIT_BASH_PATH` in `settings.json` `env` points it at `bash.exe`. Native install: `%USERPROFILE%\.local\bin\claude.exe`, versions in `%USERPROFILE%\.local\share\claude`; npm install ships the same native binary. Source: https://code.claude.com/docs/en/setup (fetched 2026-09-25).
- Gemini CLI: hooks spawned with `spawn(shellConfig.executable, [...argsPrefix, command], { shell: false, env })`, env = `sanitizeEnvironment(process.env, sanitizationConfig)` + `GEMINI_*`/`CLAUDE_PROJECT_DIR` + per-hook `env`. Source: https://raw.githubusercontent.com/google-gemini/gemini-cli/main/packages/core/src/hooks/hookRunner.ts (fetched 2026-09-25). On Windows the shell is `powershell.exe -NoProfile -Command`: https://geminicli.com/docs/tools/shell/ (via search, 2026-09-25). Timeout in ms, only `type: "command"`, events include `BeforeAgent`/`AfterAgent`/`AfterTool`/`SessionStart`/`SessionEnd`/`Notification` (no `UserPromptSubmit`): https://geminicli.com/docs/hooks/ (fetched 2026-09-25). Sanitization redacts names/values matching sensitive patterns unless in `security.allowedEnvironmentVariables`: https://geminicli.com/docs/reference/configuration/ (via search, 2026-09-25).
- Codex CLI has hooks (`SessionStart`, `SessionEnd`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `UserPromptSubmit`, `Stop`, ...), with a Windows-only `commandWindows` override; feature key `hooks` (alias `codex_hooks`). Source: https://learn.chatgpt.com/docs/hooks (redirect of developers.openai.com/codex/hooks, fetched 2026-09-25). None of grok, opencode, pi, amp is wired for hooks in Tars.

### 5.2 node-pty on Windows

- ConPTY is used when Windows build >= 18309 unless `useConpty: false`; `useConptyDll` (experimental, default false) loads node-pty's bundled `conpty.dll` + `OpenConsole.exe` instead of the inbox one. Source: local `node_modules/node-pty/lib/windowsPtyAgent.js:30-45`, `typings/node-pty.d.ts:94-110` (node-pty 1.1.0 as installed).
- Relative `file` is looked up in the *parent's* `Path` without PATHEXT, then `CreateProcessW(NULL, cmdline, ...)`: `src/win/conpty.cc:275-287`, `:413-424`; `src/win/path_util.cc:53-92`. Proved: `/bin/bash` -> "File not found:", `npx` / `claude` -> "Cannot create process, error code: 2".
- `pty.process` on Windows = `opts.name || env.TERM` (`lib/windowsTerminal.js:44`, `:103`, `:182`). Proved: `"xterm-256color"`.
- Bracketed paste: inbox ConPTY re-parses input; Hyper moved to node-pty 1.1.0 with `useConptyDll: true` (bundled ConPTY 1.23.251008001) and a contributor measured pastes "2 of 6 broken with the inbox ConPTY, 14 of 14 intact". Source: https://github.com/vercel/hyper/pull/8210 (2026-08-22). Related unresolved report on build 26200: https://github.com/herdrdev/herdr/issues/4263 (2026-09-16).
- `AttachConsole failed` uncaught in `conpty_console_list_agent` on kill, surfacing as an Electron error dialog: https://github.com/openai/codex/issues/25272 (2026-05-30); also openai/codex#25372, #25415, anomalyco/opencode#32389 (search 2026-09-25). Reproduced here.
- Prebuilds for win32-x64 and win32-arm64 ship in the 1.1.0 package (local listing); no Electron-44-specific ConPTY issue found.
- Typing into PowerShell 5.1 over ConPTY: an LF inside a quoted string splits the input (proved, section 5.4).

### 5.3 Spawning `.cmd` / `.bat` and resolving binaries

- CVE-2024-27980 (2024-04-10): Node 18.20.2 / 20.12.2 / 21.7.3 and later throw `EINVAL` when `spawn`/`spawnSync` is given a `.bat`/`.cmd` without `shell`; revert flag strongly discouraged. Source: https://nodejs.org/en/blog/vulnerability/april-2024-security-releases-2 . Electron 44 (Node 24) has it.
- libuv (`child_process` on Windows) ignores PATHEXT and only appends `.com` then `.exe`, so `spawn('npm')` is ENOENT when only `npm.cmd` exists. Sources: https://github.com/libuv/libuv/blob/v1.x/src/win/process.c ; https://github.com/cline/cline/issues/14446 (search 2026-09-25).
- cross-spawn solves PATHEXT, shebangs, spaces and shim escaping by resolving the command and wrapping in `cmd.exe` with escaping: https://github.com/moxystudio/node-cross-spawn (fetched 2026-09-25). Its `cmd.exe` path still inherits the 8191-char and no-newline limits.
- Recommended safe pattern (Claude docs above say the same): resolve the command with PATH x PATHEXT; if it is an `.exe`, spawn it directly; if it is an npm `.cmd` shim, read the shim (npm cmd-shim format, last line runs `"%_prog%" "%dp0%\node_modules\<pkg>\<bin>.js" %*`) and spawn `node.exe <script> ...args`; only as a last resort `cmd.exe /d /s /c` with a single audited escaper, refusing args with newlines. `where.exe` is not needed: a pure Node resolver over `process.env.Path`/`PATHEXT` is faster, testable and avoids a subprocess (use `where.exe` only in diagnostics).

### 5.4 Local proofs (commands run, nothing written in the repo)

- `bash -c 'C:\Windows\System32\whoami.exe'` in Git Bash: `C:WindowsSystem32whoami.exe: command not found` (127); quoted: works.
- Git Bash: `command -v curl jq` -> `/mingw64/bin/curl` only; `curl -H @<(printf "X-Tars-Test: 1") http://127.0.0.1:9/` -> `option -H: error encountered when reading a file`, exit 26; plain `-H` -> exit 7 (connection refused, i.e. it would have sent).
- Node 22 + repo node-pty: `pty.spawn('/bin/bash')` -> `File not found:`; `pty.spawn('npx')`, `pty.spawn('claude')` -> `Cannot create process, error code: 2`; `p.process` -> `"xterm-256color"`; PATH override seen by child when parent key is `PATH`.
- node-pty into `powershell.exe -NoLogo -NoProfile`, typed `Write-Output 'line1<LF>line2'; Write-Output DONE<CR>` -> PowerShell tried to run `line2'; Write-Output DONE` as a command (CommandNotFoundException). Killing the exited PowerShell raised `Error: AttachConsole failed` from `conpty_console_list_agent.js:13`.
- node-pty into `cmd.exe /d`: `cd /d "%USERPROFILE%" && echo A B` works.

## 6. Decisions

### Decision 1: hooks. A) bash + Git Bash + jq, B) Node `.mjs`, C) Claude HTTP hooks

**A. Keep bash, require Git Bash (+ jq).**
- Needs: Git for Windows (optional for Claude, docs 5.1), a `jq.exe` (not present; bundle or install), rewriting the auth header in all 16 scripts (25 `-H @<(...)`, #8) to `-H @-`/`--config -`, quoting the command paths (`claude-provider.ts:218`, `gemini-provider.ts:194`, `statusline.ts:309`), and for Gemini an explicit `bash.exe "<path>"` command because Gemini runs hooks in PowerShell (#10). CRLF risk on checkout (no `.gitattributes`). `umask` meaningless.
- Diff: ~16 scripts (every one touched for the header) + 3 TS sites + a jq bundling story. The script edits also change mac/linux behaviour (header mechanism), so byte-identical darwin is lost unless forked scripts are kept.
- Risk: two hard external deps on Windows, MSYS path conversion surprises, one bash per hook (slow start on Windows: ~100-300 ms per bash + curl + N jq processes per event).

**B. One Node hook runner (`hooks/tars-hook.mjs <event>`, plus `statusline.mjs`).**
- Node >= 18 has `fetch`, `JSON`, `URLSearchParams`: removes curl, jq, awk, stat, process substitution, and fixes #13/#14 for free. Node is already a Tars requirement (`mcp-orchestrator.ts:117-118`, `:415`).
- Wiring: Claude exec form `{ "type":"command", "command":"node", "args":["<abs>/tars-hook.mjs","session-start"], "timeout":30 }` (no shell, no quoting, works with or without Git Bash); if the installed claude predates `args` (open question), shell form `node "<abs path>" session-start` is valid in Git Bash and in PowerShell alike. Gemini: `node "<abs path>" after-agent` (PowerShell `-Command` parses it), plus `env` / `security.allowedEnvironmentVariables` for the token (#12).
- Diff in upstream files: `claude-provider.ts` hook table + command builder (~20 lines), `gemini-provider.ts` (~20 lines), `statusline.ts` script body swap (~10 lines TS + new `.mjs`); new files `hooks/*.mjs` (~350 lines incl. transcript parsing). Migration: `configureHooks` must replace the old `.sh` entries (its probe matches on file name, `:223`).
- mac/linux risk: none if gated to win32 in the fork (`.sh` kept byte-identical elsewhere); if later proposed upstream for all platforms, behaviour must be proved equal (same routes, same bodies) by an E2E that records hook posts. Node process start (~40 ms) is cheaper than bash + curl + 3-6 jq.

**C. Claude `type: "http"` hooks straight to the Tars API.**
- Zero process, zero runtime: Claude POSTs its own payload; `headers: { Authorization: "Bearer $CLAUDE_MGR_API_TOKEN", "X-Tars-Agent": "$CLAUDE_AGENT_ID" }` with `allowedEnvVars`. SessionStart context comes back in the response body.
- Needs new server routes that accept Claude's native payloads (today's routes take Tars-shaped bodies) and move transcript parsing server-side; URL fixed per Tars instance (API_PORT at write time: fine, each sandbox has its own HOME). Does not help Gemini (command only) or the statusline.
- Diff: `hooks-routes.ts` (+~150 lines), `claude-provider.ts`. Upstream-worthy, but a server-contract change owned upstream.

**Recommendation: B**, gated to win32 first (`hookCommand(file, event)` in `electron/platform/`), `.sh` untouched on mac/linux, then propose B for all platforms upstream (it also fixes the Gemini token and URL-encoding bugs everywhere). Keep C as the upstream follow-up for Claude.

### Decision 2: provider launch. A) per-OS generated script, B) env in Node + direct spawn

Ground truth: no live path uses a generated script (#29); env is already built in Node (section 2). The Windows work is the executor and the argv.

**A. Generate `.ps1`/`.cmd` per launch.**
- `.ps1`: execution policy (`-ExecutionPolicy Bypass` needed), PS 5.1 has no `&&`, prompt must be embedded safely (here-string edge cases), file on disk holding the prompt and possibly keys. `.cmd`: 8191-char line, no newline in args, `%`/`^` expansion (BatBadBut). Both keep a shell between Tars and the CLI, so `cliRunningIn` stays blind (#6). New code in 20 providers or a new serializer. Rejected.

**B. Env in Node + direct spawn of the CLI in the ConPTY.**
- B1 (recommended, minimal upstream diff): a platform function `toLaunch(cliCommand, cwd, env)`: on darwin/linux returns today's `{shell:'/bin/bash', args, typedLine}` unchanged; on win32 it (1) tokenizes the provider's POSIX string back to argv with a strict `posixWords()` (the grammar is closed: single-quoted words with `'\''`, bare flag/validated tokens; `exec-into-cli.test.ts` already pins it), (2) resolves `argv[0]` with PATH x PATHEXT, `.cmd` shim -> `node.exe <script>`, (3) builds the MSVCRT command line itself (#26) and spawns it as the PTY's process with `cwd` (no `cd`, no `exec`, no typing: fixes #3, #4, #27). `spawnAgentPty` records `runsCommand: true` explicitly (not `args.includes('-c')`), which makes `cliRunningIn` correct on Windows (#6). `typeLaunch`/`launchInTerminal` on win32 respawn the PTY with the CLI (the `local` switch already does exactly this, `ipc-handlers.ts:594-647`).
  - Providers changed: 0 of 20. Upstream files touched: `agent-routes.ts` (~8 lines), `ipc-handlers.ts` (~10), `bot-core.ts` (~6), `agent-manager.ts` (~6), `agent-pty.ts` (~6), `kanban-generate.ts` (~10, argv spawn), `path-builder.ts` (~10). About 60 lines in 7 upstream files + ~300 lines of new platform code and its failure-first tests.
  - mac/linux risk: none by construction (darwin/linux branch returns the current values; the existing exec-into-cli and pty tests stay the regression net).
  - Cost: the tokenizer is a second parser of the providers' output; any future provider that emits shell syntax fails loudly (test over all providers on every platform).
- B2 (cleaner, bigger): change the contract to `buildInteractiveArgs(params): string[]` and derive the POSIX string with one `quotePosix(argv)`. Same Windows behaviour, removes the tokenizer, but edits all 20 providers (~300 lines) and the 3 provider test files: high conflict surface with upstream. Good upstream PR later, not for the fork.

**Recommendation: B1 now**, propose B2 upstream with the Windows support issue. Do not port or regenerate the dead `buildScheduledScript` family; propose its removal upstream.

### Decision 3: default shell (human terminals; agents get no shell under decision 2)

Where a shell is still spawned on Windows: quick terminal (`pty-manager.ts:855`, `ipc-handlers.ts:2920`), `pty:create` (`ipc-handlers.ts:185`), plugin installer (`ipc-handlers.ts:1537`), cli-paths detection (`cli-paths-handlers.ts:47-48`, audit B).

| Option | Pros | Cons |
|---|---|---|
| `pwsh.exe` (PowerShell 7) | modern, `&&`, UTF-8 default, good PSReadLine | not installed by default (absent here) |
| `powershell.exe` 5.1 | always present on Windows 10/11 | no `&&`, LF-in-quotes splits input (proved), slower start |
| `cmd.exe` (`%ComSpec%`) | always present, fast, `&&` works (proved) | poor UX, no UTF-8 by default, 8191 limit |
| Git Bash | same syntax as mac, typed POSIX lines would work | optional dependency (not guaranteed), WSL `bash.exe` shadows it on PATH (CONVENTIONS), MSYS path mangling, still no foreground-process tracking |

- Args must become per-shell: `-l` is valid only for bash/zsh. `-NoLogo` for PowerShell, `/d` or nothing for cmd.
- The plugin installer should not go through a shell at all on Windows: its `INSTALL_SHAPES` are argv-able (`claude plugin ...`, `npx skills add ...`) via the resolver of decision 2.
- Diff: `default-shell.ts` (+~15 lines: win32 order `appSettings.terminalShell` > `pwsh.exe` on PATH > `powershell.exe` > `%ComSpec%`), a new `shellArgs(shell)` beside it, and 4 call sites replacing `['-l']` (~4 lines). A Settings picker is a visible change: Nicolas decides; the setting can ship without UI first.
- mac/linux risk: none (`env.SHELL ||` darwin/linux branch unchanged, `shellArgs` returns `['-l']` for them).

**Recommendation:** `pwsh.exe` when found, else `powershell.exe`, overridable by a setting (Git Bash selectable there); never a shell for agent CLIs.
